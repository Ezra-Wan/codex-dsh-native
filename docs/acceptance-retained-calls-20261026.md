# 主实例 v14 验收失败与 v15 返修（2026-10-26）

用户已授权继续修复、安装和真实验收；新增要求是节制网络流量。第二实例保持关闭，复用本地依赖；本轮返修没有新增模型请求、依赖安装或运行时下载。

## 实际观察与判定

| 项目 | 证据 | 判定 |
| --- | --- | --- |
| peer 直接进入侧边 | 主实例 `ds_observe_peer` 打开既有历史，用户回答“直接在侧边打开原生历史”；诊断为 fullscreen | 通过，只限该宿主版本 |

## 已复现的实现缺陷

1. `TaskRouter.resolveTask` 合并历史调用时，整份磁盘 summary 会覆盖有效运行时 URL/世代。修为只合并调用范围与历史结果，优先取活跃记录的范围。
2. 已结束任务的历史运行时启动中，第二张卡片可能在 URL 尚未采集时提前返回，误报无原生页面。现在复用并等待既有 URL 采集，不再启动第二个进程或 prompt。
3. 原组件 `receive` 虽保留 `entryTask`，但仍把后续工具结果直接交给 `present`，可将第一轮流内显示切到第二轮。现在原流内归属固定，侧边仍使用完整原生日志。可选宿主 widget state 只保存 agent/call 两个编号；无此能力时不宣称跨重挂持久化。

前三条均有修前失败、修后通过的针对性检查，另保留真实原生装配器与范围过滤检查。它们不能独自证明旧入口已在 Codex 内恢复。

## 8801 的来源与修复

只读进程/监听核对证实，8801 和 8802 当时由同一个当前桥接控制器的 `sdk-web` 子进程监听，是两条已打开历史所用的原生服务。未杀端口占用者，也未证明此前每次占用都属于同一原因。

旧默认分配从8801开始，只知道本控制器已经分配的端口，无法保证跨控制器安全。DSH 安装包 `dsh-host-webserver@0.2.1-rc.2` 原生支持 `port: 0`，其 `getOrigin()` 返回实际绑定端口；现默认直接复用，由操作系统持有并分配空闲端口，不做“先探测空闲、关闭、再绑定”的竞态流程。历史冷恢复同样默认使用0，URL/patch文件按任务和运行时世代命名，避免两任务覆盖 `0.json`。显式非零 `CODEX_DSH_WEB_BASE_PORT` 仍是旧区间兼容模式。

实际用真实 Cordis、两个真实上游 WebServer 和真实 adapter 同时绑定回环接口，确认两个已绑定端口不同且真实 URL 写出，随后销毁测试服务。未启动展示浏览器、未调模型。

## 宿主边界及复验顺序

- 前端版本 v15 / `0.1.3-preview.3`，保留 v14 资源别名供旧入口解析；不能保证宿主丢失的旧卡片状态可由插件补回。
- 官方[可选 widget 状态](https://developers.openai.com/plugins/build/chatgpt-ui)说明的是宿主扩展；必须检查当前 Codex 是否实际提供，不能把 ChatGPT 支持当作 Codex 保证。
- 页面检查工具初始化因模块兼容错误失败；没有使用非授权浏览器替代，也没有据此宣称已自动完成界面验收。
- 先确认实际主 MCP 已重载至新版本，再零模型打开第一轮并切换显示位置；随后检查第二轮独立显示、第一轮重开及侧边完整历史。
- 需要时补新的执行中流和双 peer 取证；旧入口先修好，避免用更多模型请求掩盖恢复问题。
- 原主实例重启记录停在 closing，但之后只读核实了不同的新主 PID 和新工具。记录残缺，不能宣称自动重启助手全程成功；任何下一次重启必须再核对无活动/unknown任务及新 PID。
