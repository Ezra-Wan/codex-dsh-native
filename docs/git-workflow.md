# Git 工作流规则（本项目强制）

依据 2026-10-24 gitflow 复核（`.local/gitflow-review-20261024/REVIEW.md`）落档。核心教训：分支使用本身合格，**提交粒度**不合格——一次实现提交混入多个可独立回滚的功能，回滚其一会连带撤销其余。

## 分支

- `main` 是稳定分支；**任何改动先开分支**（含 docs/chore——没有"太小不值得开分支"的例外，小分支成本低）。
- 命名：`feat/<主题>`、`fix/<主题>`、`docs/<主题>`、`chore/<主题>`。
- 合并一律 `--no-ff`，合并说明写明：具体行为变化、如何验证、未验收项。
- 合并后删除特性分支；已合并推送的历史**永不重写**（不 rebase/reset 已推送的 main）。

## 提交粒度（本规则的灵魂）

一个提交 = **一个可独立回滚、可独立审查的行为变化**。判据（满足其一就应拆分）：

1. **回滚判据**：评审人可能想单独撤销其中一部分（修 bug A 时不想连带撤掉修 bug B）；
2. **二分判据**：出问题时 `git bisect` 定位到的应该是一个明确行为，而非"一批修好的几件事"；
3. **审查判据**：一份 diff 能用一句话说清"它改变了什么"。

实现与其测试**同提交**（回滚即整体回滚，不留红测试）。fixture/资产迁移与依赖它的代码切换**分两个提交**（先入库资产、后切引用，中间点测试仍绿）。

## 提交信息

格式：`type[(scope)]: 中文主题`（type ∈ feat/fix/docs/test/chore/refactor/perf）。正文写动机与验证方式，不写"修改了若干文件"。

## 钩子

`git config core.hooksPath .githooks` 启用 commit-msg 格式检查（克隆后执行一次）。

## 反例存档

`63c2c81`（fix/consolidation-review）：iframe 恢复 + 会话写入标记 + worker 分流 + 主题迁移/测试/文档，混为一个提交——回滚 worker 分流会连带撤掉已修复的 iframe 保护。正确做法是 3-4 个原子提交（见复核报告"后续适合的拆分"）。
